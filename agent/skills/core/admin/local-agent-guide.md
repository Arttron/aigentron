# Local agent (reference — answer from this, never guess)

The **Local agent** tab of **🧩 Add-ons** (`/addons?tab=local-agent`). A small program, `aigentron`, runs on the PERSON'S OWN computer (macOS / Linux; a Windows archive is built, not yet tested) and keeps one outbound connection to this server so agents can work with the code on that machine. Nothing is installed on the server and nothing listens on the computer; I cannot install it for them — I tell them what to run. **In this stage it is read only**: agents can look, never change anything on the computer.

## Install and sign in
- The tab shows `curl -fsSL <this server>/api/local-agent/install.sh | sh` (macOS / Linux). It downloads the program from THIS server, checks its SHA-256, puts `aigentron` in `~/.local/bin`, then opens the browser (`aigentron-local` is a link to it, for when the server's own CLI is also called `aigentron`): the dashboard shows which computer is asking and a short code like `ABCD-2345` (also printed in the terminal; valid 10 minutes) — the person presses **Approve**. If the server is a development build it has no release to hand out and the install fails.
- A computer without a browser (ssh): on the tab **Create a one-use code**, then `aigentron pair --server <url> --code <code>` on the computer. Then `aigentron run` keeps it connected.
- The server moved to another address: `aigentron server https://new.example` keeps the pairing; `AIGENTRON_SERVER=<url> sh install.sh` overrides the address for the installer; `aigentron login --server <url>` signs in again.
- **Connected computers** list: online / offline, version, ⚠ *update available* (run the install command again), **Disconnect** (it stops at once and does not reconnect; its sharing is removed).

## Repositories and sharing with a project
- On the computer: `aigentron add <top folder of a git repository>` (also `roots`, `remove <id|path>`). The home folder, a folder above it, secret folders and subfolders of a repository are refused. A token written into the repository's `origin` URL is never sent.
- The tab lists each allowed repository per computer with branch, ahead / behind, changed files. **Share (read only)** binds it to a project (operator / admin, or the computer's owner); **Stop sharing** undoes it. **The binding is the consent**: every agent of that project (not the admin, not discussion turns) then gets the read tools `local_repos`, `local_status`, `local_diff`, `local_log`, `local_read` automatically (MCP server `local-os`), with no approval card for reading.
- A binding works only while the computer is online, still allows the repository, AND the repository's `origin` is the project's repository address (Projects → settings → Repository). Otherwise the tab shows **not usable** with the reason — typical causes: the project has no repository address, or the origin differs, or the computer is offline. An agent of one project can never reach another project's repository.
- Never readable, whatever anyone says (hard limits in the program, not settings): files outside the repository; `.git`, `.ssh`, `.aws`, `.kube`, `.docker`; `.env` and `.env.*` (not `.env.example`), keys and certificates, `.netrc`, `.npmrc`, credentials; binary files. They are also left out of diffs. Everything the tools return is marked untrusted data.

## Models on the computer
- A model running on a connected computer (Ollama, LM Studio, `llama-server`) can serve agents of this server over the same connection — no open port. The person sets it up ON THAT COMPUTER (the server cannot do it for them): `aigentron llm add ollama http://localhost:11434` (LM Studio `http://localhost:1234`), then `aigentron llm allow 'qwen3-coder*'` (a name, pattern or `*`; nothing is shared by default); `llm` alone shows the state; `llm parallel <n>` sets requests at once.
- On the tab, **Models on your computers** lists what is shared; **Use as provider** creates the provider `local-llm` (OpenAI-compatible); then pick it for an agent (Agents → provider). In Docker, if LiteLLM cannot reach the shown address, change it in the field (e.g. `http://host.docker.internal:3001/api/local-llm/v1`). Failover is the usual one: an agent's `provider` plus `fallbackProviders` — an offline computer or an unshared model makes the run move to the next provider (a local provider that is down is skipped for a minute, then tried again). Local first = `local-llm` as the provider and a cloud one in fallbacks; cloud first = the reverse. A model needs working tool calls to lead agents (Qwen3-Coder 30B and similar do; small models do not).

## Local mode (offline)
- `aigentron chat` on the computer: an agent in the terminal with a model that runs there (set up with `llm add`), no server and no internet needed. Works in one allowed repository; reads freely (never secret files) and asks `apply [y/N]` before every edit, new file or commit. `chat -p "<request>"` without a terminal only reads. It is separate from the server's tasks — nothing from a local session reaches the server yet. Use a model with working tool calls (Qwen3-Coder 30B works on a 36 GB Mac).

## Rules
- **Rules** section of the tab (operator / admin): snapshots, fetch, fast-forward, notifications, propose-a-commit, quiet time after typing, extra ignore patterns. **Save and sync** pushes them to every computer at once (offline ones get them when they connect); the tab shows how many online computers have the latest revision. A computer keeps the copy in `rules.global.yaml`.
- A repository can carry `.aigentron/local.yaml` with the same keys. A project file may switch a rule OFF, tune numbers, add ignore patterns and make the quiet time LONGER; it may switch a rule ON only if the global rules tick that rule under "A repository may switch on". `aigentron rules --repo .` shows the effective values and why anything was ignored. Reachable folders and approval requirements are hard limits, never rules.
- These rules are only configured so far: the engine that acts on them (snapshots, fetch, fast-forward, commits) comes in the next stage, so changing them has no visible effect yet. Say so if asked.

# How agents create work (reference — answer from this, never guess)

**Tools of a lead agent** (the agent of a top-level task, such as `pm`). A subtask's agent has NONE of `create_subtask` / `check_subtasks` / `complete_subtask` / `create_task` (it still has `report_task_status` and `schedule_check`):
- `create_subtask {prompt, title?, agent?, after?}` — splits THIS task into a part that runs on its own. `after` = ids of EARLIER subtasks (of the same lead) that must be done first: the new one is held (status `queued`, no job; the task page says what it waits for), starts by itself when they are done with their results in its context, and is `blocked` (the lead is woken) if one of them failed or was cancelled/deleted. Without `after` subtasks start at once and run in parallel as far as Settings → concurrency allows (at 1 they take turns). It always lands in the parent's project; it has NO `project` and NO `standalone` option. By default at most 25 OPEN subtasks per task (done / cancelled / failed ones do not count) and 100 in total (`SUBTASK_LIMIT` changes both). An equivalent open subtask is returned instead of a duplicate.
- `check_subtasks` (status + latest result of its subtasks), `complete_subtask {id}` (accept one of its own), `schedule_check` (re-run itself later), `report_task_status`.
- `create_task {project, prompt, title?, agent?}` — a NEW top-level task in a project (any live project; `default` for the default one). Only for a LEAD whose file has the line `createTasks: true` OR the skill `task-splitting` in its `skills:` (that skill also teaches when to split work out: 3+ subtasks on one theme, or a subtask that needs its own breakdown); every call is approved on a card; an equivalent task already waiting / running / ready in that project is returned instead (an accepted one does not block starting the work again). It is NOT a subtask: `check_subtasks` does not list it.

**Step limit.** An agent's file may have `maxTurns: 80` (5–500; default 40 for everyone): how many steps one run may take before it must report or ask the person to continue. Give leads that plan big work more; the Agents form has the field.

**Fetching code.** The same agents have `fetch_remote {branch?}` (no approval): the orchestrator runs `git fetch` with the project's key, then the agent merges `origin/<branch>` itself — a `git fetch` / `git pull` from an agent's shell always fails (`Host key verification failed`) because it holds no credentials. **Pushing code.** Agents of a code project with a remote have `push_branch {branch, to?, reason}`: a person approves each push, the orchestrator pushes with the project's key (agents hold none, so a `git push` from their shell always fails). Never forced; works on local branches only.

**Where a task lives.** A task's project is set when it is created (New task form, the project's default agent, or `create_task`); its subtasks inherit it. `propose_task` (mine) makes a subtask of this chat by default (when this chat is itself top-level), or with `standalone: true` a top-level task in the DEFAULT project — it has no project option.

**To let an agent start tasks in projects:** `propose_agent` with the skill `task-splitting` in `skills:` (or `createTasks: true`) in its frontmatter (the dashboard form cannot set it; a later edit in the form keeps it). Tell the person each task still needs their approval.

**Accuracy rule.** Say what the references above and `admin-tools` document. If something is not documented there (a tool option, a file name, a setting), say "I don't see that documented" and offer to check with `agents_list` / `agent_get` — do not invent options, flags or file paths.

## Moving an agent to another Aigentron
**Agents → Export** on an agent downloads `<name>.agent.json`: the agent file + the custom skills it lists + any custom/learned skills the person ticks (learned skills are shared by all agents and may hold project/client details — warn). No keys or secrets. **Agents → Import** reads the file, shows a plan (new / same / different / blocked), and writes only new items; a differing local item is replaced only when "overwrite mine" is ticked (old copy snapshotted). The name can be changed; `admin` and shipped skill names are blocked; `createTasks` is not carried over. Check the provider/MCP/skills the agent uses exist on the target. The whole server: `aigentron export/import`.

## Escalation ladder
An agent may list `escalation: provider/model, provider/model` (cheaper → stronger; Agents page → Escalation, models listed cheapest first with tier and price where known). It starts on its own model; if the run reports `failed`, runs out of time or steps, the task continues in a fresh session on the next step (never for `blocked` — that needs a person — and not for follow-up messages). A red verification gate uses the ladder too: the first auto-fix stays on the agent's model, later attempts climb the steps. A step that is unavailable is skipped; `fallbackProviders` are tried only when no step is available.

## Scheduled work: a script first
For anything on a schedule, ask: are the steps the SAME every time (fetch a rate, compute, draw a chart, post it)? Then recommend a **script schedule** (main menu → Schedules → *Run a script*), not a task for an agent: no model cost, no steps to lose, and a small model often fails at multi-step jobs (a background run, «I will report later», a stalled run). A script keeps history in `$LDS_DATA_DIR` and the files it leaves in `$LDS_OUTPUT_DIR` (a chart) are sent to the chat and deleted (`docs/schedule-scripts.md`, example `docs/examples/fx-chart.py`). I cannot create a script schedule or write files: offer to give a developer agent the task of writing and testing the script (`propose_task`), then tell the person to add it under Schedules. Keep a `task` schedule only when the run needs judgement (reading, deciding, explaining).

## Notes and shared files (safeguards)
Project memory (`memory/`), the project's note library and the brief are written only through tools: agents use `workspace_note` (appends) and `workspace_save`; a hand-written change (Write, Edit, a shell redirect, a patch) is refused, nothing is lost. For a library note use `propose_resource`: **append** adds only new lines (history, logs); **update** `text` replaces the whole note and is refused when it would drop most of it unless `replace: true`; the old text is kept as a version (last five). A scheduled run that used no tools gets a ⚠ line under its report. Examples in prompts: use placeholders (`<rate>`), a small model copies real-looking numbers.

## Model strength (`tier:`)
The platform guesses a model's strength (price from the gateway, local models by size, else the name): `cheap` / `mid` / `top`. An agent file may set `tier: cheap|mid|top` (Agents form → *Model strength*). A `cheap` run gets a short «work carefully» note in its system block and is asked before it starts tasks (`create_task`, `propose_task`) even when approvals are off; every model is refused hand-written changes to memory / library / brief. Stats → *How runs ended, by model* shows where a small model fails.

## Детали по ключевым находкам

### E-01 — дубль Authorization в `workspace.service.ts`
`git show 678ae5c` подтверждает: `http.extraHeader` многозначен; значение из `.git/config` (`configureCredential`) + значение из `GIT_CONFIG_*` → два заголовка → 400. Исправлен только `github.service.ts` (там теперь `GIT_CONFIG_COUNT=2`, первая запись пустая — сброс списка). В `workspace.service.ts:143-152` по-прежнему `COUNT=1` без сброса, и именно этим env идёт `fetch` (`:65`) при каждом `ensure()` после первого клона. Ошибка глотается `.catch(warn)`, поэтому в логах будет только «fetch failed: …», а worktree создаются от старого `origin/<branch>`.

### E-02 — таймаут прогона против ожидания человека
`timer` (`:527`) ставится один раз на 600 с и снимается только по завершении. `ask_user` (`questions.service.ts:60-71`) блокирует tool call до 3600 с по умолчанию; approval — до `approvalTimeoutSeconds` (до 3600). Idle-watchdog специально пропускает `tool_use` и pending approvals (`run-guards.ts:22`, `executor:539-542`), но жёсткий потолок не знает об ожидании. Минимальное исправление: хранить `deadlineAt`, при событиях `tool_use` с `toolName === ASK_USER_TOOL`/`approval-created` запоминать `waitStart`, при `tool_result`/`approval-resolved` прибавлять ожидание к дедлайну; таймер пересоздавать.

### E-03 — cancel сливает очередь follow-up
Сценарий: задача running, пользователь отправил ещё сообщение (ушло в `PendingFollowUp`), потом нажал «Отмена». `cancel()` → `setStatus('cancelled')` → `drainPendingFollowUp` → `runFollowUpNow` → `setStatus('queued')` + enqueue → потом `executor.cancel`. Старый воркер получает `errored` outcome, читает статус `queued`, не терминальный → ставит `stalled` и пишет `error`. Новый job запускается и ставит `running`. Пользователь видит «отменённую» задачу живой.

### E-04 — порядок блоков system prompt и кэш
`appendSystemPrompt = orientation(+projectMap) + SOUL + instructions + skills + roster + memory` (`:166-177, 217`). Комментарий на `:175` («memory LAST so the static part stays cacheable») правильный по замыслу, но orientation с картой файлов стоит первой и меняется чаще memory (любой созданный файл). Перестановка — чистая правка строк 166-177/217 без изменения смысла.

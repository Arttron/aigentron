# Экономия токенов и лимитов подписок (план)

Цель: меньше расходовать лимиты подписочных планов (Claude, Codex) и токены по API-ключам. Исследование (роутер, кэш, batch, сжатие) сверено с кодом; Batch API для подписок не применим.

## Шаг 1. Замер (2026-11-02)
Данные стенда: 58 запусков (08.10–02.11), 50 из них админ-чат на `gpt-4o-mini`; кэш не отчитывается (`cache_read = 0`).

| Ходов в запуске | Запусков | Среднее входных токенов |
|---|---|---|
| 1 | 30 | 32 800 (мин. 24 700) |
| 2 | 8 | 56 000 |
| 3 | 6 | 78 000 |
| 4 | 4 | 102 000 |
| 5 | 2 | 152 500 |

Выход в среднем 163 токена. Вывод: **базовая «обвязка» ≈ 25–33 тыс. токенов на запуск, и каждый следующий ход добавляет ещё ≈ 25 тыс.** (без кэша вход пересылается заново).

Состав обвязки (оценка 1 токен ≈ 4 символа):
- внутренние MCP-инструменты: обычный агент 27 шт ≈ **4,8 тыс.**; админ 63 шт ≈ **11 тыс.** (самые тяжёлые: propose_schedule, propose_batch, look_at, video_digest, propose_resource, metrics_report, create_task, ask_user);
- `SOUL.md` 15,5 КБ ≈ 4 тыс. (в каждый запуск); `admin.md` 8,5 КБ ≈ 2 тыс.; навыки админа до 48 КБ ≈ до 12 тыс.;
- встроенные инструменты Claude Code, реестр коллег, браузерные инструменты (при подключённом расширении).
Кэш-дружелюбность промпта уже продумана (`prompt-layers.ts`: system неизменен, переменное — в сообщении).

## Порядок работ
1. ✔ Замер (этот документ).
2. Урезание обвязки: инструменты по роли/режиму, SOUL на ядро + блоки, навыки по требованию.

5. Роутер: правила → (при необходимости) дешёвый классификатор; эскалация вверх; лог решений.
6. Сводки длинных сессий дешёвой/локальной моделью; свежая сессия вместо бесконечного resume.

## Построено (2026-11-02): шаг 4 — настраиваемые фильтры
- Ядро `packages/shared/src/compress.ts` (`compressText`, `normalizeCompression`): пробелы, повторы строк, цитаты и подписи, base64/hex, длинные логи (голова + хвост), лимит длины, собственные regex-правила; считает экономию по правилам.
- Настройки: Settings → Work → Compression (`AppSettings.compression`, JSON), с окном «Try it».
- Применение: сообщение человека агенту и ответы «толстых» внутренних инструментов (`kb_*`, `read_document`, `resources_search`, `workspace_files`, `look_at`, `video_digest`, `check_subtasks`); транскрипт хранит оригинал. Не охвачено: ответы `browser-ext` (снимки страниц) и сторонних MCP — следующий шаг.
- Статистика: колонки `AgentSession.compression{Before,After,Saved}`; на Stats — блок «Saved by our text filters» (по фильтрам и по проектам), а вид «By project» получил график токенов.

## Построено (2026-11-02): эскалация по моделям
- `escalation: provider/model, …` в агенте (лестница от дешёвой к сильной). Цепочка запуска: основная → ступени → fallback-провайдеры, то есть fallback используется, только когда недоступны все ступени. Ступень, провайдера которой нет, и дубли пропускаются; для последующих сообщений (follow-up) лестницы нет.
- Эскалация по результату (`worthEscalating`): отчёт `failed`, нехватка времени/шагов или собственная ошибка — задача продолжается в свежей сессии на следующей ступени с заметкой о том, что сделано. `blocked` (нужен человек), отмена и остановка по памяти не эскалируются.
- Ранжирование моделей по цене: `GET /api/providers/:name/models` теперь отдаёт `info` (ступень cheap/mid/top, цена за млн токенов, источник), отсортированный от дешёвых; цены берутся из публичной карты цен LiteLLM (кэш 6 ч), локальные модели — free, подписки и неизвестные — по имени. В форме агента подписи у моделей и редактор лестницы.
- Не сделано: эскалация по провалу verification gate (он вне цикла исполнителя), статистика эскалаций на Stats, цена вручную.

- Эскалация по verification gate (2026-11-02): первая авто-правка после красного гейта идёт на модели агента, следующие (`verifyMaxAttempts`) — по ступеням лестницы (`escalateTo` = номер попытки − 1) в свежей сессии с исходным запросом задачи. Оговорка: если задача уже была поднята по лестнице самим запуском, первая правка гейта всё равно идёт на основной модели. Заметка о передаче (`handoff`) теперь доходит до модели (раньше эскалация по результату показывала её только в транскрипте).

## Построено (2026-11-02): режим «Вопрос» (шаг 3 плана)
- Задача `kind: 'ask'` (поле уже было, миграции задачи не нужно): чекбокс «Just a question» в форме новой задачи, `/ask` в Telegram, фильтр «Questions» в списке. Лёгкий цикл как у чат-агента: без worktree, verification gate, контракта статуса; своя полоса очереди (`lane: chat`), по завершении задача уходит в `review`.
- Модель вопросов: Settings → Work → Questions (`AppSettings.askModel`, `provider/model`); пустое значение = модель самого агента; модель, закреплённая за задачей (`/model` в чате), главнее; лестница эскалации агента продолжает работать.
- Не сделано: вопрос по умолчанию в Telegram (обычное сообщение по-прежнему продолжает активную задачу или создаёт задачу), кнопка «повысить вопрос до задачи», минимальный набор инструментов для вопроса.

## Построено (2026-11-02): статистика эскалаций и вопросов (шаг 7 плана, часть)
`AgentSession.escalationReason/escalatedFrom` (причина и «откуда») + блоки «Escalations» (по причинам и путям from→to) и «Questions» (число, токены, цена) на Stats, с учётом фильтра по проекту. Вес лимита подписки по агентам по-прежнему не показывается.

- Настройка канала «A plain message starts» (`defaultMode`: task | ask): что становится обычным сообщением без активной задачи. `/ask` всегда вопрос, `/new_task` всегда задача, файл всегда задача; при активной задаче сообщение по-прежнему продолжает её. Скользящее сжатие диалога вопросов (новая сессия после N реплик/паузы) не сделано: `/clear` начинает заново.

## Построено (2026-11-02): справочник админа как база знаний (пункт 2 плана)
- Системная база `admin-reference` (`KnowledgeBase.system = true`): сидер `AdminReferenceService` при каждом старте режет руководства `agent/skills/core/admin/*.md` на разделы `##` и синхронизирует базу по хэшу текста (добавляет новое, заменяет изменённое, убирает исчезнувшее; без изменений — ничего не делает). Видна только агенту `admin`, только для чтения (людям — 403 на правку/удаление/добавление, агентам `kb_add` закрыт); в интерфейсе баз помечена «Built in».
- Админ вместо 45 КБ руководств в промпте держит оглавление (файл: разделы) и правило «сначала `kb_search` по базе, отвечать только по найденному»; learned-навыки по-прежнему вставляются. Если база не готова (первый старт, нет файлов) — руководства вставляются целиком, как раньше. Оглавление детерминировано (кэш промпта не ломается).
- Проверка поиска на настоящих руководствах — 10 типовых вопросов должны находить нужный раздел в первых 4 результатах (тест `admin-reference-core.test.ts`).
- Обновление руководств: правьте `agent/skills/core/admin/*.md` как раньше; база пересобирается при старте оркестратора (`docker compose restart orchestrator`).
- Не измерено: реальная экономия токенов и качество ответов админа на живой модели — нужен прогон 15–20 вопросов до/после.

## Исправление после ревью и прогона 5 вопросов (2026-11-02)
Первая версия (админ ищет сам через `kb_search`) на `gpt-4o-mini` без кэша была **хуже** прежней: 3–5 ходов, 48–95 тыс. входных токенов на вопрос против ~33 тыс., и один ответ неверный (карточка «Questions» обрезалась лимитом 700 символов в выдаче поиска). Теперь:
- **Подбор разделов на сервере.** Для админа оркестратор сам ищет в `admin-reference` по сообщению человека и кладёт 4 самых подходящих куска целиком в само сообщение (кэш системного промпта не меняется); `kb_search` остаётся для одного уточняющего поиска.
- **Мелкие документы.** Длинные разделы режутся по карточкам (`- *Name*:`) и рецептам (`**Name.**`); база нарезана кусками по 1200 символов, выдача этой базы не режется до 700.
- **Результат повторного прогона тех же 5 вопросов:** 1 ход и ~23,7 тыс. входных токенов на вопрос (было 48–95 тыс. и ~33 тыс. исходно), ответ на проблемный вопрос верный.
- Строгая проверка поиска: 12 вопросов, нужный факт должен быть в первых 4 кусках (тест `admin-reference-core.test.ts`).
- Источник руководств при старте — копия релиза (`shippedAgentDir`), а не живая папка (она обновляется другой задачей старта).

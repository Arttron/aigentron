# Модель работы с сервисом (анализ и проект)

> Статус: ПРЕДЛОЖЕНИЕ (2026-10-12). Основано на проверке кода и живого стенда. Ничего из «Предложения» ещё не построено.
> Цель: чтобы и короткий вопрос, и проект на недели (например, «создание устройства»), и задача «искать и следить» шли по понятному,
> дешёвому и предсказуемому пути.

## 1. Что есть сейчас (проверено)

| Что | Как устроено |
|---|---|
| **Задача** (Task) | единая сущность: чат = задача. У задачи агент, статус, сессии, события, подзадачи (`parentId`), ссылки на другие задачи (`TaskLink`), очередь сообщений. |
| **Жизненный цикл «работа»** | для любого обычного агента: worktree + ветка → запуск → обязательный `report_task_status` → verification gate → push/PR. |
| **Жизненный цикл «чат»** | только для агента с `mode: chat` (так работает admin): без worktree, без gate, ответ = результат. |
| **Декомпозиция** | лид (`pm`) создаёт подзадачи (`create_subtask`) или зовёт специалистов (Task tool), результаты собираются обратно (fan-in). |
| **Память** | сессия (resume) в пределах задачи; итоги подзадач/ссылок; общая библиотека **Resources** (всем агентам); **базы знаний** (поиск); обученные навыки. |
| **Автоматика** | расписания (`kind: message|task`, `taskMode: same|new`, тихие часы), каналы (Telegram), вопросы человеку (`ask_user`), подтверждения. |
| **Наборы** | пакеты агентов + ресурсов + выключенных расписаний: English, Renovation, Software team. |
| **Рабочая папка** | ОДНА на весь сервер: Settings → repo URL / ветка / подпапка. |

## 2. Что показала проверка

**Живой тест.** Обычному агенту (`helper`, GPT-4o-mini) задан вопрос «Столица Франции? Одно слово.»
Результат за 11 с: ответ «Paris.» есть, но задача завершилась **`failed`** («ended the run without calling report_task_status»), агент
сам отчитался `failed`. Пользователь видит ❌ на правильный ответ.

Найдено (по убыванию важности):

1. **Нет режима «вопрос».** Любой вопрос к обычному агенту проходит весь «рабочий» цикл (контракт статуса, worktree, gate, PR). Слабая
   модель путает контракт статуса — и простой ответ превращается в `failed`. Режим «чат» есть, но это свойство *агента*, а не *запроса*.
2. **Нет сущности «Проект».** Одна рабочая папка и одна библиотека на весь сервер. Два параллельных проекта (устройство + ремонт) делят
   папку, ресурсы, базы знаний, команду и канал уведомлений. Задачи — плоский список.
3. **Нет памяти проекта.** Между задачами проекта живут только краткие итоги и ссылки. Решения, требования, открытые вопросы, словарь
   теряются; длинная сессия раздувается (resume всё тянет за собой).
4. **Слежение («искать и мониторить») — это просто расписание.** Нет состояния «что уже видели», нет определения «новое/изменилось»,
   нет порога «сообщать только если…», нет истории и дайджеста. `same` копит бесконечный диалог, `new` всё забывает.
5. **Telegram: «обычное сообщение продолжает активную задачу».** Все вопросы сваливаются в одну сессию (растёт контекст и цена), а чтобы
   начать новое, нужно помнить про `/clear` и `/new_task`.
6. **Лид «только координирует».** Правило из SOUL относится к лиду по умолчанию; на простой вопрос он может запускать делегирование
   вместо ответа.
7. **Рабочая ветка не про задачу.** В общем режиме задача-вопрос получила прицепленную чужую ветку из рабочей папки.
8. **Нет бюджета.** Расход виден по провайдерам, но не по задаче/проекту; нет лимита на проект и на слежение.

## 2a. Принято (2026-10-12): `done` ставит только человек

Агент, закончив работу, переводит задачу в **`review`** («готово — подтвердите»). В **`done`** задачу переводит человек: кнопкой «Mark as done»
(дашборд, Telegram), командой `/done` или явной фразой («готово», «done», «задача завершена» — короткое сообщение целиком). Любое другое
сообщение продолжает задачу. Подзадачи принимает их лид (они заканчиваются `done` автоматически). Заблокированную/застрявшую/упавшую
задачу тоже можно принять «как есть». Старые `done` остаются.

## 3. Предлагаемая модель

### 3.1 Четыре формы работы

| Форма | Когда | Цикл | Память | Результат |
|---|---|---|---|---|
| **Вопрос** (Ask) | «что/как/сколько», короткий диалог, уточнение | лёгкий: без worktree/gate/PR, без обязательного статуса | скользящий диалог чата, сам сжимается | ответ в чате |
| **Задача** (Task) | один результат: документ, правка, расчёт | рабочий (как сейчас), при необходимости с worktree | итог задачи → проект | артефакт + итог |
| **Проект** (Project) | недели работы, несколько ролей, этапы | набор задач + общая память + этапы | **память проекта** | план, артефакты, журнал решений |
| **Слежение** (Watch) | «искать и следить»: цены, новости, нормы, наличие | по расписанию, лёгкий цикл со **состоянием** | история находок | уведомление «только новое/важное» + дайджест |

Любая форма может быть внутри проекта. Для разовых дел есть проект «Входящие» (по умолчанию, невидим, пока не нужен другой).

### 3.2 Проект как контейнер
Проект = **команда** (набор агентов) + **рабочая папка/репозиторий** + **память** + **ресурсы и база знаний** (своя область) +
**расписания/слежения** + **канал уведомлений** + **бюджет**. Создаётся из **пакета** (сейчас пакеты ставят агентов и ресурсы глобально —
станут проектными).

**Память проекта** (файлы в папке проекта, короткая выжимка подмешивается в промпт каждого агента проекта):
- `brief.md` — цель, ограничения, критерии успеха, кто принимает решения;
- `plan.md` — этапы (вехи) и их статус;
- `decisions.md` — журнал решений (дата, кто решил, почему); ответы человека на `ask_user` попадают сюда автоматически;
- `open-questions.md`, `glossary.md`, `status.md` (одно-экранный статус для людей и лида).
Агентам — инструмент `project_note` (дописать решение/вопрос/факт), без подтверждения (файлы проекта, не код).
Большие материалы (даташиты, нормы, исследования) — в **базу знаний проекта**, не в промпт.

### 3.3 Этапы и контрольные точки
Проект идёт по этапам; на границе этапа лид формирует «пакет решения» (что сделано, что решено, что открыто, что предлагается дальше) и
запрашивает человека (`ask_user`: «Идём дальше / Доработать / Остановить»). Без этого длинный проект расползается.

### 3.4 Слежение (Watch)
Отдельный вид расписания со структурой: **что искать** (запросы/URL/источники), **что считать новым** (дедупликация по хэшу в базе
знаний слежения), **как сообщать** (`on_change` / `threshold` / ежедневный-еженедельный дайджест), **история** (находки с датой и источником).
Запуск — лёгкий цикл без worktree: поиск → сравнение с историей → запись нового → решение «сообщать ли». В канал уходит только
значимое; всё остальное — в дайджест. Инструменты: `watch_seen` (проверить/записать «видел»), поиск и `kb_add` для истории.

### 3.5 Как человек работает с этим (интерфейс)
- **Одна строка ввода**: по умолчанию «Вопрос». Рядом: «Задача», «Проект», «Слежение», «Обсуждение». Вопрос можно одной кнопкой
  **повысить** до задачи/проекта (контекст переходит).
- **Telegram**: обычное сообщение = вопрос в «скользящем» диалоге (после N реплик или паузы сам сжимается/начинается заново);
  `/task текст`, `/project`, `/watch`, `/discuss`.
- **Список**: сгруппирован по проектам; в проекте — этапы, открытые вопросы, ожидает решения человека, расход.
- **Правила цены**: вопросы идут на дешёвой модели по умолчанию; тяжёлые модели — для задач/проектов; лимит расхода на проект/слежение.

## 4. Как это выглядит на примерах

**А. Короткий вопрос** («какой допуск у резьбы M6?»). Ask → дешёвая модель → ответ с ссылкой на базу знаний, если есть. Без worktree,
без статуса, без PR. Если ответ превращается в работу — кнопка «в задачу».

**Б. Поиск и мониторинг** («следи за ценой и наличием датчика X у 5 поставщиков, сообщай если цена −10 % или появился на складе»).
Watch: источники, порог, расписание (раз в 6 ч, тихие часы). Каждый запуск: собрал → сравнил с историей → записал → сообщил только
при пороге. Раз в неделю — дайджест. История — в базе знаний слежения; расход ограничен.

**В. Проект «создание устройства»** (пример: носимый датчик). Команда из пакета «Hardware»: менеджер проекта, системный инженер,
электроника, прошивка, механика/корпус, закупки/BOM, тестирование, соответствие нормам (CE/FCC), исследователь.
Этапы и контрольные точки: 1) требования и ограничения → 2) концепция и архитектура → 3) подбор компонентов (**слежение** за ценами и
наличием) → 4) схема/плата (описание цепей, список компонентов, правила разводки; файлы САПР — вне агентов) → 5) прошивка (код в
репозитории проекта, тесты) → 6) корпус и механика (требования, чертёжные описания) → 7) план испытаний → 8) сертификация (чек-листы,
база норм) → 9) передача в производство. На каждом этапе: артефакты в папке проекта, решения в журнале, открытые вопросы
человеку кнопками, статус одним экраном. Мозговой штурм/споры архитектора и электронщика — режим **обсуждения**.

**Г. Проект разработки ПО** — то же, но папка проекта = git-репозиторий, задачи работают в worktree, gate = тесты/линтер, PR на задачу.

## 5. План внедрения (по шагам, каждый полезен сам по себе)

| Шаг | Что | Зачем | Размер |
|---|---|---|---|
| **0** | Режим **Вопрос** для любого агента: лёгкий цикл, без обязательного статуса; Telegram — вопрос по умолчанию | исправляет проверенный дефект (`failed` на верный ответ), удешевляет вопросы | малый |
| **1** | **Проект**: сущность, «Входящие», привязка задач, своя папка, свои ресурсы/БЗ/расписания/канал; список по проектам | изоляция и порядок | средний |
| **2** | **Память проекта** + `project_note` + автозапись ответов `ask_user` + инъекция выжимки в промпт | длинные проекты не теряют решения | средний |
| **3** | **Слежение** со состоянием, порогами и дайджестом | сценарий «искать и мониторить» | средний |
| **4** | **Этапы и контрольные точки** + статус-экран | управляемость проекта | средний |
| **5** | **Бюджет** по задаче/проекту/слежению | предсказуемая цена | малый |
| **6** | Пакеты **Hardware** и **Monitoring** (+ «Software team» → проектный) | быстрый старт сценариев | малый |

Решения, которые нужны от владельца, — в конце сообщения в чате (порядок шагов и границы первого релиза).

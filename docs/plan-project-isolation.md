# План: изоляция проектов разных клиентов (2026-10-25)

**Зачем.** На одном сервере проекты разных клиентов. Данные, код, секреты и сессии одного клиента не должны быть видны ни агентам, ни людям другого клиента.

## Что есть сейчас (проверено по коду)

- **Изоляция агентов от сервера** (S-01, `aigentron harden`, `AGENT_RUN_AS_UID/GID`): агенты работают от одного непривилегированного пользователя; база, `secrets`
  и оркестратор ему недоступны, при старте это проверяется. На каждый запуск этот пользователь получает в собственность папки задачи (`chownPlan` в
  `agent/agent-user.ts`): домашний каталог запуска, папку проекта, вложения, рабочую копию или worktree.
- **Между проектами изоляции на уровне ОС нет:** один uid на всех. Файлы, которые uid уже получал, остаются его собственностью, и агент любого проекта их читает.
  Разделение только «мягкое»: корни записи в классификаторе апрувов, вложения и медиа только своей задачи, ресурсы и базы знаний с областью «проект».
- **Люди:** у пользователя только роль (`operator | reviewer | task_setter | admin`), доступа «к проекту» нет — список задач, апрувы, статистика и поиск видят всё.

## Что общее между проектами и может протечь

| что | где | риск между клиентами |
|---|---|---|
| uid агентов | `AGENT_RUN_AS_UID` | читают и пишут файлы друг друга |
| права папок | `<data>/projects/<slug>` 0755, вложения `<data>/agent/attachments/<task>` 0755 | любой локальный процесс читает |
| **выученные навыки** | `agent/skills/learned/` | знание одного клиента попадает в промпты другого (но **общий опыт должен остаться**, см. «Опыт» ниже) |
| определения агентов, провайдеры, MCP-серверы | глобальные | токены в заголовках MCP видны всем, кто может править |
| браузер-аддон (профиль `agent`) | один профиль | куки и входы одного клиента видны всем → решено: один личный, клиентам он не выдаётся |
| Playwright-аддон | изолированные сессии | ок (профиль не хранится) |
| дашборд | роль без привязки к проекту | любой оператор видит чужие задачи, расшифровки, апрувы |
| админ-чат | видит всё платформы | по замыслу, но нужен выбор: админ клиента или админ платформы |
| расходы, ключи LiteLLM | общие | затраты по клиенту — отчёт по проектам (решено, ключей на проект не делаем) |
| порты предпросмотра 3200–3203 | общий пул | видны по localhost всем |

## Это опция, и только там, где платформа это умеет (решение 2026-10-25)

Две независимые опции, обе **выключены по умолчанию**:

| опция | что делает | где доступна |
|---|---|---|
| **Агенты: отдельный пользователь ОС на проект** (этап 1) | uid на проект, права 0700, самопроверка | только там, где сервер это умеет (см. проверку ниже) |
| **Люди: доступ только к своим проектам** (этап 2) | принадлежность пользователей проектам, фильтры в списках, апрувах, сокете, поиске | везде (логика приложения), включая dev-машину и Docker |

**Проверка поддержки** (при старте, результат в `GET /api/system/capabilities` → `projectIsolation: { supported, reason, enabled }`, виден в Settings → General и `aigentron doctor`):
Linux; процесс от root; есть `setpriv`; файловая система данных умеет `chown` и права (не macOS/Windows, не bind-mount Docker Desktop, не NFS с root-squash — проверяется пробным
`chown` во временной папке); базовая изоляция агентов (S-01) включена и рабочая; диапазон uid проектов не пересекается с записями `/etc/passwd`. Любое «нет» даёт `supported: false` и причину простыми
словами.

- **Где не поддерживается:** переключатель в Settings неактивен с причиной рядом; `PUT` включения отвечает 400 с той же причиной; миграции остаются (колонки пустые), поведение прежнее.
- **Где включено, а платформа потом перестала подходить** (сервер переехал, том сменился): безопасный отказ, как в S-01 — запуски изолированных проектов не стартуют с причиной, а не тихо
  идут под общим пользователем.
- **Выключение:** проекты возвращаются к общему пользователю агентов (владелец папок меняется при следующем запуске, как и при включении).
- Тесты: проверка поддержки — чистая функция от «фактов о системе» (подставляются в тестах), поэтому для macOS/Windows/Docker поведение проверяется без самих систем.

## Этапы

1. **Слой ОС (главное).** Отдельный uid на проект из зарезервированного диапазона (например, 40000 + номер проекта) — `setpriv --reuid=<число>` работает без записи в `/etc/passwd`,
   так что `useradd` на каждый проект не нужен. `Project.runAsUid/runAsGid` (миграции Postgres и SQLite), выдаётся при создании проекта; `chownPlan` и `prepareRun` берут uid проекта;
   папка проекта, checkout, `worktrees/<slug>` и вложения задачи — 0700 владельцу-проекту (оркестратор, root, видит всё). Самопроверка при старте расширяется: uid проекта A **не может**
   прочитать папку проекта B (и наоборот). `aigentron doctor` показывает. Миграция существующих проектов — первый запуск каждого перезаписывает владельца (план `chown` это уже делает).
   Ограничение: только установка на хосте (bare-metal / minimal); при Docker — тот же механизм внутри контейнера, но проверить.
2. **Данные и люди (опция, на любой платформе).** Принадлежность пользователей проектам (`ProjectMember`: пользователь, проект, роль в проекте); фильтры по доступным проектам в списке задач, апрувах, вопросах,
   поиске, статистике, базе знаний, ресурсах, расписаниях и во всех событиях сокета (иначе в потоке чужие названия); глобальный admin видит всё; админ-чат клиента работает только
   в пределах его проектов (его `current_context` и инструменты сужаются); Telegram-канал привязывается к проекту; журнал доступа.
3. **Общие ресурсы.** Выученные навыки с областью «проект» (по умолчанию проект, а не глобально); MCP-серверы и их секреты с областью «проект» (глобальные остаются для общих);
   агенты и провайдеры: «доступно проектам» (список), ключ провайдера с отдельным ключом LiteLLM на проект (раздельные расходы и лимиты); профиль браузер-аддона на проект
   (`profiles/<slug>`); порты предпросмотра по пулу на проект.
4. **Жизненный цикл.** Бэкап и восстановление по проекту (`aigentron backup --project`), удаление проекта стирает всё (папки, вложения, расшифровки, базы знаний, uid), срок хранения
   расшифровок и вложений на проект.
5. **Проверка.** Набор «враждебных» тестов: агент проекта A пытается прочитать/записать проект B (`cat`, `ls`, симлинк, `/proc`, общий `/tmp`), прочитать секреты, вложения чужой задачи,
   чужие выученные навыки; пользователь клиента A открывает задачу клиента B (API и сокет). Каждый должен быть отказом.

## Опыт остаётся общим (решение 2026-10-25)

Требование: выученные навыки («опыт») по-прежнему полезны всем проектам. Различаем **опыт** (как чинить ошибку, как структурировать работу) и **данные клиента** (названия, домены,
репозитории, пути, ключи, код): протечка — это когда второе попало в первое.

- **Два уровня:** общие навыки платформы + проектные. Агент видит оба. Учится он в **проектный** уровень по умолчанию (виден только проекту — чистить нечего).
- **Продвижение в общие** только шагом «обобщить» платформенного админа: проверка на идентификаторы исходного проекта (название, домены, URL репозитория, e-mail, IP, пути, похожее на
  ключ; найдено — нельзя продвигать, пока не вычищено), переписывание в обобщённый вид, в карточке апрува видна **разница** исходного и обобщённого, затем апрув. Место для шага —
  плановая консолидация навыков (`propose_learned_skill`, снимки, бюджет уже есть).
- **Происхождение:** у каждого общего навыка записан проект-источник (виден только платформенному админу): при уходе клиента можно проверить и убрать выросшее из его проекта.
- **Сводный опыт без текста клиента:** закономерности (что часто останавливается, где ошибаются инструменты) — метриками, без содержимого.
- Предложение по умолчанию: новые навыки из клиентских проектов **не попадают в общие автоматически**, только продвижением админа.

## Порядок и объём

Этап 1 даёт защиту данных на диске между агентами разных клиентов и делается первым (≈ изменения в `agent-user`, миграция, самопроверка, тесты; безопасно включать по проекту).
Этап 2 нужен, как только в дашборд зайдёт кто-то, кроме вас (сейчас доступ ко всему у любого оператора). Этап 3 закрывает утечки через общие настройки. Без этапов 1 и 2 вместе
изоляция клиентов неполная; без этапа 3 — остаётся утечка через выученные навыки и общий браузерный профиль.

## Решения владельца (2026-10-25)

1. **Дашборд:** сейчас заходит только владелец, в будущем сотрудники и клиенты. Значит: этап 1 (ОС) делаем сейчас; этап 2 (доступ людей) откладываем, **но готовим основание**: вся
   выдача данных проходит через одно место «какие проекты видит пользователь» (пока возвращает все), чтобы позже включить фильтр, не переписывая каждый список.
2. **Навыки:** общие остаются; из проекта в общие **только вручную**, и нужен **дифф опыта**: экран, где для проекта видно, какие его навыки новые относительно общих и какие отличаются
   (с построчной разницей), найденные идентификаторы клиента подсвечены, рядом кнопка «продвинуть» (с обобщением и апрувом).
3. **Браузер-аддон: один личный** (часть личного ассистента). Клиентские проекты работают с браузером только через аддон Playwright (изолированные сессии, ничего не хранится): профиля на
   проект не будет, а агентам клиентских проектов браузер-аддон не выдаётся (проверка при назначении MCP/инструментов — этап 3).
4. **Расходы: только отчёт по проектам** (токены и стоимость задач уже хранятся, задача знает проект; `metrics_report` принимает `project`). Ключей LiteLLM на проект и лимитов не делаем.

## Найдено при проработке: проверки и предпросмотр идут от root

`VerificationService` (`verifyCommands` проекта) и `PreviewService` (`npm install && npm run dev` рабочей копии) запускают команды **от root** с `HOME` оркестратора — даже при включённой
изоляции агентов (S-01). Код, который агент мог изменить, выполняется с правами оркестратора. Для клиентских проектов это закрывается в этапе 1: проверки и предпросмотр идут от uid проекта
(а при включённой только базовой изоляции — от общего пользователя агентов), с домашним каталогом запуска.

## 1. Stefan Knoch — 10 воркфлоу

1. Архитектура: ИИ как старший архитектор предлагает варианты и задаёт вопросы; итог в `ARCHITECTURE.md`.
2. Каркас интерфейса в v0 или Bolt.new, затем экспорт в IDE и больше не править в генераторе.
3. Парное программирование в IDE, сохранённые правила «так больше не делать».
4. Тесты: сгенерировать, прогнать, вернуть ошибки ИИ.
5. Отладка: если ИИ не справился за две попытки, искать ошибку вручную.
6. Документация: README, справочник API, changelog из каждого слитого PR.
7. ИИ-ревью каждого PR с правилами команды.
8. CI/CD и операции: генерация пайплайнов, масштабирование, откаты.
9. Онбординг: `ONBOARDING.md` и объяснение подсистем.
10. Ретроспективы: боли команды отдавать ИИ.

**Предупреждения автора:** ИИ-тесты покрывают в основном счастливый путь; не спорить с генератором о библиотеках; не зацикливаться на повторах. Цифры «3–10×» без данных. Про секреты, права и стоимость автоматических деплоев и откатов не сказано ничего.

## 2. Ola Prøis — воркфлоу, которым пользуется сам

1. Перед кодом обсудить идею с несколькими ИИ (архитектура, исследование библиотек, второе мнение).
2. PRD: проблема, функции, критерии приёмки; пропустить через другие ИИ.
3. Разбить PRD на задачи с зависимостями (Task Master, MCP).
4. Подтягивать актуальную документацию библиотек (Context7, MCP), чтобы не было выдуманных API.
5. В репозитории: `ai-context.md` (до 100 строк: модули, типы, идиомы, ловушки) и `index.md` (карта документов, одна строка на файл).
6. Свежий чат на каждую задачу + короткий handover-документ; в конце задачи ИИ переписывает handover для следующей.
7. Проверять запуском, а не чтением каждой строки.
8. Языки со строгим компилятором (Rust) дают ИИ быструю обратную связь.

**Предупреждения:** длинные чаты дрейфуют; ИИ уверенно говорит «должно работать», когда не работает («trust but verify»); поддержка handover требует усилий. **Возражения из комментариев:** пропуск построчного ревью опасен; тесты стоит писать по критериям приёмки до реализации; CI на каждую задачу.

## 3. ZDNet — 6 бытовых воркфлоу

Сценарии: сводка новостей, отладка кода (найти причину, минимальный безопасный фикс, проверить), прогноз погоды со списком вещей, учёт чеков из почты в таблицу, речь в текст, напоминания по обслуживанию дома.

**Как создавать воркфлоу** (шаги автора):

1. Описать ручной процесс.
2. Найти узкие места.
3. Выбрать способ ИИ.
4. Определить источник данных и контекст.
5. Собрать минимальную версию и проверить.
6. Добавить ограничения и дорабатывать.

Пример в AnythingLLM: название, описание с примерами фраз запуска и форматом ответа, переменные, блок скрапинга и блок инструкции для LLM. Статья вводная, про личное использование.

## 4. Приклеенная статья: безопасность агентов (прогноз Google на 2027)

1. Алерты поднимаются выше по цепочке: агенты сами обогащают и сортируют, человек видит проверенный вывод.
2. **У каждого агента своя идентичность, минимальные права, журнал каждой операции, права отзываются.**
3. Отравленные зависимости, которые ИИ-ассистенты тянут сами; безопасность должна быть внутри конвейера разработки, а не в конце.
4. Red-team самих агентов: у ИИ новая поверхность атаки.

## Что не берём

- Task Master и Context7: есть BACKLOG и планы, API стека стабильны.
- Генераторы интерфейсов (v0, Bolt): есть своя дизайн-система.
- «Не читать код, только тестировать»: для кода, который выполняет команды на машинах пользователей, не годится.

## План

1. `CLAUDE.md` (40–60 строк) и `docs/index.md`. Только документация. В `CLAUDE.md`: релизный ритуал, общие UI-компоненты, лимит гайда админа (16 000 символов), запрет `execFileSync` в e2e, правило «после двух неудач остановиться и спросить», «протокол меняется вместе с примерами в `packages/shared/protocol`».
2. Обновить протокол (примеры + тесты на обеих сторонах) и `plan-local-agent.md`.
3. Проверить тесты на обход правил доступа, добавить недостающие.
4. Журнал операций локального агента и `aigentron log` (код агента, нужен релиз).

Пункты 3–4 меняют агента и требуют релиза только по команде владельца.
